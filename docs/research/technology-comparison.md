# Сравнение технологических решений MedPredict

Дата проверки: **16 октября 2026 года**. Цель — обосновать текущую архитектуру учебного проекта и отделить реализованное от предварительных решений. Сравниваются четыре решения, для каждого рассмотрены три варианта. Оценки применимости — выводы для этого репозитория; универсального рейтинга технологий и неподтверждённых измерений производительности здесь нет.

## Основание и статусы

Перед сравнением изучены [AGENTS.md](../../AGENTS.md), [package.json](../../package.json), [README](../../README.md), [HTTP-адаптер](../../src/api/http.ts) и [предварительный контракт](../api-contract.md).

- **Выбрано и реализовано:** React + TypeScript + Vite на frontend; обмен HTTP/JSON в клиентском адаптере; хранение пользовательского ввода в памяти интерфейса.
- **Предварительно:** Java/Spring Boot указан в распределении работ команды, но сервер отсутствует в этом репозитории; GET описания модели предложен frontend и не утверждён backend-командой.
- **Не выбрано для текущего этапа:** альтернативы ниже. Это не означает их техническую непригодность.

В `package.json` объявлены React `^19.2.0`, TypeScript `~5.9.3`, Vite `^7.2.0`, Vitest и Playwright. Диапазон зависимости не означает последнюю доступную или фактически установленную версию. Этот анализ не меняет версии.

Общие критерии выбора: соответствие сценарию «форма → один запрос → числовой результат», совместимость с готовым кодом, стоимость интеграции и сопровождения, проверка данных и ошибок, возможность тестирования, границы ответственности участников. Защита медицинских данных определяется реализацией и эксплуатацией всей системы, а не названием framework.

## 1. Frontend: React, Vue или Angular

| Вариант и статус | Подтверждённые возможности | Применимость и ограничение для MedPredict |
|---|---|---|
| **React + TypeScript + Vite — выбрано, реализовано** | React строит интерфейс из компонентов и предоставляет состояние и обработку событий. [React Quick Start](https://react.dev/learn) | Уже существуют страницы, общие компоненты, hooks сценария, локализация и проверки. Можно завершать интеграцию без переноса интерфейса. React сам по себе не проверяет ответ сервера: репозиторий отдельно разбирает данные в `src/api/contract.ts`. |
| **Vue — не выбрано** | Декларативный интерфейс, реактивность, Single-File Components; поддержка SPA и постепенного внедрения. [Vue Introduction](https://vuejs.org/guide/introduction.html) | Разумный вариант для такого размера приложения. Замена потребует переписать JSX-компоненты и hooks, повторно проверить фокус, отмену запросов и локализацию; подтверждённой потребности в таком переносе нет. |
| **Angular — не выбрано** | Компоненты, dependency injection, routing, формы и инструменты CLI. [Angular Overview](https://angular.dev/overview) | Подходит при потребности в едином полном framework и его соглашениях. Здесь свои небольшие навигация и форма уже работают; переход потребует другой структуры приложения без выявленного выигрыша для текущего сценария. |

**Решение:** сохранить React. Причина — соответствие задаче и готовой реализации, а не заявление о том, что он быстрее или безопаснее Vue/Angular. В данном исследовании не выполнялись сравнительные сборки, измерение размера bundle или испытания этих альтернатив.

## 2. Backend: Spring Boot, FastAPI или Node.js

| Вариант и статус | Подтверждённые возможности | Применимость и ограничение для MedPredict |
|---|---|---|
| **Java / Spring Boot — предварительное решение команды** | Spring поддерживает REST-контроллеры и преобразование объектов в JSON; официальный пример показывает HTTP GET и запуск Spring Boot. [Spring REST Guide](https://spring.io/guides/gs/rest-service/) | Совпадает с зоной ответственности Оралхана и ожидаемым интерфейсом frontend. Но реализация, версия Java/Spring, валидация, auth, способ вызова модели и эксплуатация здесь не проверены. Называть backend готовым нельзя. |
| **Python / FastAPI — не выбрано как основной backend** | OpenAPI, автоматическая документация и валидация на основе Python-типов/Pydantic. [FastAPI Features](https://fastapi.tiangolo.com/features/) | Может быть удобен, если модель обслуживается в Python. Это условие, а не установленный факт о модели Али. Замена основного backend изменит договорённость команды; отдельный inference-сервис нужен только при подтверждённой необходимости. |
| **Node.js с HTTP-сервером — не выбрано** | JavaScript runtime с асинхронным I/O и встроенным HTTP-сервером. [Node.js Introduction](https://nodejs.org/en/learn/getting-started/introduction-to-nodejs) | Позволяет использовать JavaScript по обе стороны API. Нужно отдельно выбрать и реализовать серверные валидацию, auth и вызов модели. Наличие Node для Vite не означает готового Node-backend. Причин менять текущую командную архитектуру не обнаружено. |

**Решение:** документировать Java/Spring Boot как план команды и проверять совместимость по контракту. Формат модели и способ её запуска должны определить Али и Оралхан. Нельзя из выбора Java вывести обязательность Python-микросервиса, конкретного ORM или базы данных.

## 3. API: синхронный HTTP/JSON, GraphQL или gRPC-Web

| Вариант и статус | Подтверждённые возможности | Применимость и ограничение для MedPredict |
|---|---|---|
| **HTTP/JSON, REST-style — реализовано в клиенте; сквозной контракт предварительный** | HTTP определяет семантику GET/POST и коды ответа. [RFC 9110](https://httpwg.org/specs/rfc9110.html). В репозитории есть `GET /api/v1/model/info` и `POST /api/v1/predictions`. | Соответствует двум операциям и обычному браузерному `fetch`; дополнительных клиентских библиотек не требует. GET ещё нужно согласовать. Сервер обязан воспроизводить утверждённые payload, единицы и ошибки; наличие TypeScript не проверяет сетевой JSON. |
| **GraphQL — не выбрано** | Типизированная схема, выбор полей запроса, mutations, resolvers и introspection. [GraphQL Learn](https://graphql.org/learn/) | Разумно для нескольких связанных сущностей и разных потребностей клиентов. Здесь один числовой результат и небольшое описание модели: новую схему и выполнение запросов пришлось бы поддерживать сверх текущего контракта. Проверка допустимости медицинских значений всё равно остаётся отдельной задачей. |
| **gRPC-Web — не выбрано для браузера** | Контракт `.proto`, генерация клиента; официальный браузерный пример использует Envoy для связи с gRPC backend. [gRPC-Web Basics](https://grpc.io/docs/platforms/web/basics/) | Может быть уместен при существующей gRPC-инфраструктуре и нескольких сервисах. Для текущих двух запросов потребует смены формата, клиента и настройки браузерного шлюза/поддержки gRPC-Web. Необходимость этого не подтверждена; внутренний протокол будущего backend здесь не определяется. |

**Решение:** сохранить текущий синхронный HTTP/JSON. В [адаптере](../../src/api/http.ts) уже предусмотрены отмена, таймаут, `credentials: 'omit'`, `cache: 'no-store'`, проверка JSON и HTTP-ошибок. Эти свойства описывают клиент; они не гарантируют, что сервер отменяет вычисление, не сохраняет запрос или не пишет его в логи.

При интеграции сначала согласовать [контракт](../api-contract.md), затем проверить реальные GET, POST, 400, 5xx, единицы, CORS и таймаут. Если измеренная длительность inference сделает синхронный ответ неприемлемым, отдельно рассмотреть job/status API. Сейчас задержка модели не измерена, поэтому очередь задач не вводится.

## 4. Хранение: память интерфейса, PostgreSQL или SQLite

**Утверждённой базы данных в этом репозитории нет.** Сравнение PostgreSQL и SQLite — варианты для будущего серверного решения, а не описание уже созданной архитектуры.

| Вариант и статус | Возможности и ограничения | Применимость |
|---|---|---|
| **Память React без постоянного хранения — выбрано для текущего frontend** | Ввод и язык сохраняются при переходах, очищаются при перезагрузке. История аккаунта не реализована; показатели запрещено писать в localStorage/sessionStorage. [README](../../README.md), [AGENTS](../../AGENTS.md) | Достаточно для текущего анонимного сценария и demo. Не обеспечивает долговременную историю и восстановление после закрытия вкладки. Это явная граница прототипа. |
| **PostgreSQL — предварительная альтернатива, не утверждена** | Транзакции, ограничения целостности, внешние ключи, MVCC и средства восстановления. [PostgreSQL About](https://www.postgresql.org/about/) | Кандидат для серверных аккаунтов и связанной истории при конкурентной записи. Потребует отдельного развёртывания, миграций, резервирования и политики доступа. Выбор зависит от требований backend; никаких схем БД здесь не создано. |
| **SQLite — предварительная альтернатива, не утверждена** | Подходит для локального хранения и небольших серверных приложений; одновременно выполняется одна запись на файл БД. При высокой конкуренции записи разработчики рекомендуют рассмотреть client/server СУБД. [SQLite Appropriate Uses](https://www.sqlite.org/whentouse.html) | Кандидат для небольшого учебного backend на одном узле. Однописательность не делает SQLite непригодной для любого веб-приложения. Требования к нагрузке и нескольким серверным узлам пока не установлены. |

**Решение:** до согласования истории и auth сохранить текущее хранение в памяти. Серверную БД выбирает команда после определения сроков хранения, удаления, доступа, связей данных, конкурентной нагрузки и условий размещения. Выбор СУБД сам по себе не решает приватность и не разрешает хранить медицинские данные.

## Итог выбора и вопросы к команде

| Решение | Что фиксируется сейчас | Что ещё требует подтверждения |
|---|---|---|
| Frontend | React + TypeScript + Vite | Изменение стека не требуется для текущего сценария |
| Backend | Java/Spring Boot как направление работы Оралхана | Репозиторий сервера, версии, валидация, вызов модели, эксплуатация |
| API | Текущий HTTP/JSON-адаптер | Согласование GET/POST/400 и проверка на настоящем сервере |
| Хранение | Память frontend | Нужна ли история; auth, БД, сроки хранения и удаление |

Для технической защиты можно утверждать, что выбор frontend и клиентского API реализован и обоснован готовой структурой проекта. Нельзя утверждать, что уже внедрены Spring Boot, PostgreSQL/SQLite, безопасная серверная история или обученная модель.

Официальная документация альтернатив проверена на указанную дату. Их код не устанавливался и не запускался; сравнительные нагрузочные, security- и эксплуатационные испытания не выполнялись. Это документальное сравнение, а не benchmark. Сам анализ не добавляет зависимостей, не подключает интеграции и не меняет приложение.
