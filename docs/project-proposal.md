# Предложение по проекту MedPredict

Дата версии: 16 октября 2026. Рабочая тема: «Веб-прототип для воспроизводимого исследования прогнозирования медицинского показателя по табличным данным». Официальная тема, научный руководитель, целевой показатель и набор данных требуют подтверждения команды и руководителя.

## Проблема и предполагаемые пользователи

Для учебного исследования недостаточно вывести число из модели: нужно воспроизводимо связать описание признаков, проверку ввода, версию модели, результат и ограничения. Ошибочные единицы, устаревшие ответы и смешение демонстрационного примера с реальным расчётом мешают проверить такую систему.

Предполагаемые пользователи — исследователь или студент, проверяющий модель, и участник демонстрации, вводящий синтетический пример. Врач может выступать экспертом при обсуждении требований. Использование пациентами для принятия медицинских решений в текущие границы не входит. Потребность пользователей пока является гипотезой: интервью и соглашение с заказчиком не предоставлены; план проверки — в [протоколе обсуждений](research/user-validation.md).

## Цель и исследовательский вопрос

Создать учебный веб-прототип, который принимает согласованные табличные признаки, получает проверенный ответ модели через API и показывает значение, единицы и ограничения без потери данных при ошибках.

Исследовательский вопрос для последующего согласования: позволяет ли выбранный набор признаков предсказывать утверждённый показатель на отложенных данных лучше простого базового решения? В текущем примере используется систолическое артериальное давление, однако горизонт прогноза не определён. Оценка текущего значения и прогноз будущего значения — разные задачи; до фиксации целевой переменной нельзя заявлять ни одну из них как доказанный результат.

## Задачи и ожидаемые результаты

1. Проверить потребность через 3–5 обсуждений с представителями пользователей, зафиксировать требования и изменения после обсуждений.
2. Согласовать целевую популяцию, показатель, момент измерения, горизонт, признаки, доступность и условия использования данных.
3. Сопоставить исследования, существующие системы и технические альтернативы; выделить применимые ограничения.
4. Зафиксировать проверяемые требования, архитектуру и контракт между frontend, backend и моделью.
5. Соединить существующий интерфейс с настоящим backend и моделью после согласования контракта.
6. Выполнить инженерную проверку и независимую оценку модели по [плану оценки](evaluation-plan.md).

Результаты: документация и редактируемые диаграммы; запускаемый прототип; согласованный API; воспроизводимый эксперимент с baseline и честно описанными ограничениями. К 24 октября обязательны анализ, проектирование и планирование; завершённое приложение исходным заданием не требуется.

## Инженерная сложность и ограничения

Сложность состоит в согласовании версионируемого описания модели с динамической формой, проверке ответов на границе доверия, управлении конкурентными запросами, многоязычном экспорте и воспроизводимой оценке модели без утечки данных. Наличие нейросети само по себе не является результатом: выбор алгоритма должен следовать сравнению с простыми моделями.

На 16 октября есть frontend-прототип, API-адаптер и автоматические проверки. Не предоставлены утверждённые данные, клинические диапазоны, реальные метрики, интервью и отзыв руководителя. Полная готовность к предзащите зависит от закрытия [перечня незавершённых пунктов](README.md).
