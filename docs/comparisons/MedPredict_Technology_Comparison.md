# Сравнение и обоснование технологических решений MedPredict

**MedPredict — первая предварительная защита, 24 октября 2026 года**\
**Тема:** «Разработка интеллектуальной системы прогнозирования медицинских показателей на основе нейронных сетей»\
**Дата проверки репозитория и источников:** 16 октября 2026 года.\
**Статус:** обоснование реализованного frontend и предлагаемых решений backend/ML; сравнительные технические испытания альтернатив не проводились.

## 1. Основание и границы анализа

Изучены [AGENTS.md](../../AGENTS.md), [package.json](../../package.json), [README](../../README.md), [конфигурация показателя](../../src/config/indicator.ts), [HTTP-адаптер](../../src/api/http.ts), [контракт API](../api-contract.md) и существующее [сравнение технологий](../research/technology-comparison.md). Старый документ сохранён; настоящий материал дополняет его анализом моделей и способов интеграции.

Реализован React + TypeScript + Vite frontend. В `package.json` объявлены React `^19.2.0`, TypeScript `~5.9.3`, Vite `^7.2.0`, jsPDF, Vitest и Playwright. Это объявленные диапазоны, а не утверждение о последних версиях или серверной среде. HTTP-адаптер и проверка JSON существуют, но работа с настоящей моделью не доказана. Фиксированный demo-ответ не является inference.

По сообщению команды Java/Spring Boot разрабатывается Оралханом. В данном репозитории нет backend, обученной модели, ноутбуков обучения и результатов экспериментов. Следовательно, ниже Spring Boot — направление команды, MLP/LSTM и способы inference — кандидаты. Фактический опыт участников с альтернативами не оценивался: распределение обязанностей не заменяет проверку компетенций.

Рассматриваются три значимых решения с тремя альтернативами каждое. Критерии едины по смыслу: сложность разработки, совместимость, сопровождение, ожидаемые затраты вычисления, тестирование, соответствие роли команды, развёртывание и ограничения. Формулировки об ожидаемой сложности — инженерные выводы для проекта, а не измеренные рейтинги.

## 2. Решение 1: основной backend

Техническая возможность REST-контроллеров и JSON подтверждается руководством Spring; OpenAPI и проверка данных — документацией FastAPI; модульная организация TypeScript-приложения и средства проверки — документацией NestJS. [Т1](https://spring.io/guides/gs/rest-service/), [Т2](https://fastapi.tiangolo.com/features/), [Т3](https://docs.nestjs.com/), [Т4](https://docs.nestjs.com/application/validation).

**Таблица 1 — Альтернативы основного backend.**

| Критерий | Java / Spring Boot | Python / FastAPI | Node.js / NestJS |
|---|---|---|---|
| Сложность разработки | REST-контроллеры и DTO; необходимо согласовать ошибки и валидацию | Типы и схемы входа; потребуется оформить весь серверный сценарий | Controllers, modules, providers и runtime-валидация; одного TypeScript-типа недостаточно |
| Совместимость | Соответствует заявленному направлению команды; frontend обращается по HTTP/JSON | Удобен при подтверждённом Python-окружении модели; клиентский JSON совместим | Совместим с HTTP/JSON; общий язык с frontend не делает сетевой ответ проверенным |
| Сопровождение | Один Java-backend при inference внутри JVM; артефакт модели версионируется отдельно | Единое Python-окружение модели и API возможно, но его зависимости надо фиксировать | Один серверный TypeScript-проект; связь с Python/Java-моделью остаётся отдельным решением |
| Ожидаемые вычислительные затраты | Определяются моделью, преобразованиями и конфигурацией JVM; преимуществ по задержке не измерено | Определяются моделью и числом workers; `async` сам по себе не ускоряет вычисление модели | Нужно определить способ выполнения вычислений модели; название runtime не доказывает низкую задержку |
| Тестирование | Контроллеры, DTO, ошибки, CORS, модель и контракт | Схемы, ошибки, воспроизводимость окружения, модель и контракт | DTO/схемы, controllers/providers, ошибки и контракт; средства тестирования описаны в [Т5](https://docs.nestjs.com/fundamentals/testing) |
| Роли команды | Ответственность Оралхана уже указана в проекте; версия и реализация требуют подтверждения | Потребует согласовать, кто сопровождает Python API: Оралхан или Али | Потребует согласовать смену серверного стека и владельца; опыт команды не установлен |
| Развёртывание | Java-приложение; официальный пример предусматривает executable JAR | Python-сервис с зафиксированными пакетами и процессами | Node-приложение с серверными зависимостями; наличие Node для Vite не равно backend |
| Ограничения | Формат модели должен быть совместим с JVM либо нужен отдельный inference | Замена основного backend меняет договорённость команды; доступность пакетов не гарантирует безопасность | В репозитории NestJS отсутствует; перенос не обоснован выявленной потребностью |

**Предлагаемое решение:** сохранить Java/Spring Boot как основной backend по распределению ответственности. FastAPI оставить допустимым вариантом внутреннего Python inference-сервиса, если это требуется выбранной моделью. Оснований менять основной backend на NestJS сейчас нет. Это решение об интеграционных затратах и ответственности, а не о безусловном превосходстве Java.

До подтверждения решения Оралхан предоставляет версии Java/Spring, схему запросов, обработку ошибок, проверку единиц, CORS и способ вызова модели. GET описания модели в существующем контракте предложен frontend; его нельзя обозначать уже согласованным. История и auth не вводятся в архитектуру как готовые функции.

## 3. Решение 2: методы моделирования с учётом задачи

MLP и LSTM не следует выбирать как взаимозаменяемые «более точные нейросети». Выбор зависит от структуры наблюдения. Линейные модели и MLP принимают табличный вектор признаков; LSTM предназначена для последовательности и имеет рекуррентное состояние. Возможности подтверждены первичной документацией [линейных моделей scikit-learn](https://scikit-learn.org/stable/modules/linear_model.html), [MLPRegressor](https://scikit-learn.org/stable/modules/generated/sklearn.neural_network.MLPRegressor.html) и [Keras LSTM](https://keras.io/api/layers/recurrent_layers/lstm/). Их точность на MedPredict ещё не измерена.

**Таблица 2 — Три группы методов; выбор уточняется внутри каждого модуля.**

| Критерий | Простые baselines | MLP | LSTM |
|---|---|---|---|
| Сложность разработки | Для таблиц: среднее и линейная/Ridge-регрессия; для ряда: последнее значение и простой тренд | Настройка слоёв, регуляризации, оптимизатора и остановки обучения | Дополнительно окна, порядок времени, частота, пропуски, состояние и горизонт |
| Совместимость с задачей | Обязательная точка сравнения для всех модулей; конкретный baseline зависит от данных | Кандидат для Diabetes и NHANES; для ряда возможна работа с фиксированным окном | Кандидат для продольного ряда глюкозы; временная структура в табличных строках не предполагается |
| Сопровождение | Явный набор признаков/коэффициентов либо правило прогноза | Версии весов, preprocessing и гиперпараметров | Версии весов плюс правила окон, состояния, временных меток и доступности входов |
| Ожидаемые затраты | Простой контроль вычислительного бюджета; задержку всё равно измерять | Затраты зависят от размера сети и batch; преимущество по ошибке неизвестно | Длина последовательности и архитектура влияют на затраты; потребность GPU не установлена |
| Тестирование | Единый split, отсутствие утечки, MAE/RMSE и контроль единиц | Те же данные/split; масштабирование, seeds, сходимость и переобучение | Временное и, при необходимости, межпациентное разделение; запрет будущих признаков и пересечения окон |
| Роли команды | Али фиксирует протокол и обучает baseline до нейросети | Али выбирает архитектуру в пределах согласованного бюджета поиска | Али и руководитель сначала подтверждают пригодность продольных данных |
| Развёртывание | Коэффициенты/артефакт или правило; требуется тот же preprocessing | Экспорт/загрузка модели и проверка равенства вычислений | Поддержка последовательных входов; текущий API формы не описывает временной ряд |
| Ограничения | Линейная связь и простое продолжение ряда могут быть недостаточны | Нелинейность не гарантирует улучшения; результат зависит от данных и настройки | Нельзя создавать последовательность произвольной сортировкой людей; усложнение должно подтверждаться экспериментом |

**Таблица 3 — Постановка по модулям и предварительный выбор.**

| Модуль | Допустимая цель и данные | Сравниваемые методы | Что требуется до выбора |
|---|---|---|---|
| Diabetes Progression | Числовая мера прогрессирования через год после исходных признаков; scikit-learn описывает 442 наблюдения и 10 признаков. [Т6](https://scikit-learn.org/stable/datasets/toy_dataset.html#diabetes-dataset), [Т7](https://scikit-learn.org/stable/modules/generated/sklearn.datasets.load_diabetes.html) | Среднее/линейная или Ridge-регрессия и MLP; LSTM не обоснована структурой этого табличного набора | Утвердить единицы и трактовку target, split, доступность признаков и preprocessing; не называть результат диагнозом |
| Systolic Blood Pressure Estimation | САД в мм рт. ст. из NHANES; пример кодовой книги BPX_J содержит несколько последовательных измерений на осмотре. [Т8](https://wwwn.cdc.gov/Nchs/Data/Nhanes/Public/2017/DataFiles/BPX_J.htm) | Среднее/линейная или Ridge-регрессия и MLP | Выбрать цикл, популяцию, признаки и правило формирования target; повторные измерения осмотра не доказывают долгосрочную динамику |
| Glucose Forecasting | Будущая глюкоза при наличии пригодного продольного набора PhysioNet; конкретный ресурс и горизонт не выбраны. [Т9](https://physionet.org/about/) | Сохранение последнего значения/простой тренд, MLP по окну, LSTM как кандидат | Проверить доступ, лицензию, пациента, частоту, пропуски, горизонты, длительность ряда и разрешённые признаки; не обещать 30 минут по аналогии с устройством |

Число наблюдений Diabetes приводится из документации набора, а не из проведённой загрузки или обучения. Для NHANES ссылка BPX_J иллюстрирует проверяемую структуру переменных и не означает утверждения цикла 2017–2018 для проекта. Каталог PhysioNet сам по себе не подтверждает пригодность конкретных данных глюкозы.

**Предлагаемое решение:** первым экспериментом сделать baseline и небольшой MLP для Diabetes, затем расширить воспроизводимый протокол на NHANES. Glucose Forecasting реализовывать после отдельного решения по данным. Предпочтение MLP/LSTM в дипломной теме не разрешает исключать baseline или сообщать вымышленное улучшение. Если нейросеть не превосходит baseline на утверждённом тесте, отрицательный результат следует честно описать; условия доработки определяются анализом ошибок.

Разделение данных выполняется до обучаемого preprocessing. Для строгого эксперимента Diabetes нужно явно решить вопрос исходного масштабирования: `load_diabetes` по умолчанию выдаёт масштабированные признаки; `scaled=False` позволяет получить исходную форму для обучения преобразований только на train. [Т7](https://scikit-learn.org/stable/modules/generated/sklearn.datasets.load_diabetes.html). Нельзя незаметно использовать преобразования, оценённые по всей выборке, как будто они получены только на train.

## 4. Решение 3: интеграция модели с Java-backend

ONNX Runtime предоставляет Java API inference моделей ONNX. При этом наличие runtime не гарантирует экспорт любого estimator: документация scikit-learn прямо указывает неполную поддержку моделей и дополнительные затраты на пользовательские преобразования. [Т10](https://onnxruntime.ai/docs/get-started/with-java.html), [Т11](https://scikit-learn.org/stable/model_persistence.html).

Как третий технически возможный путь рассмотрен PMML с JPMML-Evaluator: официальный проект описывает вычисление регрессий и нейронных сетей в JVM. Поддержка конкретной выбранной модели, preprocessing и лицензии должна проверяться отдельно. [Т12](https://github.com/jpmml/jpmml-evaluator).

**Таблица 4 — Способы inference за Spring Boot REST API.**

| Критерий | ONNX Runtime внутри Java | Отдельный Python inference-сервис | PMML / JPMML-Evaluator внутри Java |
|---|---|---|---|
| Сложность разработки | Экспорт всей поддерживаемой цепочки, имена/типы/формы tensor, загрузка session | Python API вокруг исходной модели; внутренний контракт, таймауты и недоступность сервиса | Экспорт PMML, сопоставление схемы полей и проверка преобразований |
| Совместимость | JVM ↔ ONNX; требуется совместимость opset, runtime, платформы и модели | Может использовать исходную Python-модель, если обучение действительно выполнено в Python | Подходит для поддерживаемых моделей PMML; произвольную LSTM считать поддержанной нельзя |
| Сопровождение | Backend и файл модели разворачиваются согласованно; версии preprocessing и артефакта фиксируются | Два сервиса и два набора зависимостей; модель можно выпускать отдельно при согласованной версии | JVM и PMML-артефакт; нужны поддерживаемый конвертер и проверенные версии |
| Ожидаемые затраты | Нет внутреннего HTTP-вызова, но есть runtime и преобразование входов; фактическая задержка неизвестна | Добавляется обмен между сервисами; его вклад и затраты модели нужно измерить | Нет внутреннего HTTP-вызова; скорость не сравнивалась с ONNX/Python |
| Тестирование | Python-эталон ↔ ONNX Java на одном наборе входов; проверка типов, единиц и ошибок | Spring ↔ Python, version mismatch, таймаут и отказ; совпадение с offline inference | Python-эталон ↔ PMML Java; имена полей, пропуски, категории и преобразования |
| Роли команды | Али экспортирует и даёт эталонные ответы; Оралхан подключает runtime | Али передаёт модель и среду; Оралхан обеспечивает сервисный контракт и эксплуатацию | Али проверяет экспорт; Оралхан — выполнение в Java; команда проверяет условия лицензии |
| Развёртывание | Java-приложение и native runtime для выбранной платформы; сборку нужно испытать | Java + Python-процесс, закрытая внутренняя сеть, health/status и управление ресурсами | Java и соответствующие PMML-библиотеки; отдельный Python-процесс для inference не требуется |
| Ограничения | Экспорт и численная эквивалентность ещё не доказаны; данные пациента не входят в артефакт теста | Дополнительный компонент отказа; пакеты и происхождение артефакта должны контролироваться | Совместимость не универсальна; проект указывает AGPLv3 и альтернативное лицензирование по соглашению |

**Условное предложение:** проверить ONNX Runtime Java для первого небольшого MLP/baseline. Утвердить путь только после успешного экспорта preprocessing и модели и испытания эквивалентности. Если экспорт ненадёжен либо модель зависит от неподдерживаемых операций, рассмотреть Python-сервис. PMML — резервная альтернатива для подходящих табличных моделей; она не выбрана и не внедрена.

Нельзя называть ONNX «гарантированно безопасным» или «самым быстрым». Для всех вариантов нужны доверенное происхождение артефакта, ограниченные ресурсы и согласованные версии. Для Python особенно важно не загружать непроверенные pickle/joblib-файлы: такие механизмы могут выполнять код при загрузке. Это ограничение подтверждено документацией [Т11](https://scikit-learn.org/stable/model_persistence.html).

## 5. Проверка решения и критерии его пересмотра

До подключения настоящей модели Али и Оралхан должны согласовать паспорт артефакта: модуль, target и единицы, признаки и их порядок, preprocessing, допустимые категории/пропуски, версию и контрольную сумму файла, версии библиотек и ожидаемые формы входа/выхода. Для временного модуля дополнительно нужны частота, окно, горизонт и правило состояния. Это планируемые требования, а не уже существующий формат API.

Для приёмки интеграции предлагается контрольный набор синтетических и разрешённых обезличенных тестовых входов. Максимальное расхождение offline и deployed inference должно удовлетворять заранее утверждённому абсолютному/относительному допуску; допуск обосновывается типом данных и смыслом target. Ни конкретная величина допуска, ни успешная эквивалентность сейчас не заявляются. Ошибки схемы, единиц и версии должны выявляться, а не превращаться в правдоподобное число.

Производительность следует измерять на указанном оборудовании: отдельно загрузку артефакта, прогретый inference и полный REST-запрос; фиксировать число запросов, размер входа, конкурентность, медиану/p95, ошибки и потребление памяти. Реальный frontend-таймаут по умолчанию 15 секунд является клиентской настройкой, **не измеренным SLA и не доказательством скорости модели**. [Конфигурация](../../src/config/environment.ts).

Пересмотр способа integration требуется при неподдерживаемом экспорте, превышении согласованной задержки/памяти, необходимости другого формата входа или невозможности воспроизвести ответы. Очередь задач, GPU, контейнерная оркестрация и дополнительные базы данных не объявляются обязательными без соответствующего требования.

## 8. Границы достоверности

Альтернативные frameworks и ML-библиотеки не устанавливались; обучение, конвертация ONNX/PMML, нагрузочные испытания и тест Python/Java не выполнялись. Проверено содержание репозитория и открытая первичная документация. Технологический выбор не заменяет проверку качества данных, независимую оценку модели и анализ рисков обработки медицинских сведений.

На предварительной защите можно обосновать сохранение готового frontend, направление Java-backend, поэтапное сравнение baselines с нейросетями и критерии выбора inference. Нельзя утверждать, что все три модуля работают, что форматы уже совместимы или что выбранная технология обеспечивает клиническую точность.
