# План проверки и оценки MedPredict

Версия от 16 октября 2026. План разделяет качество программного взаимодействия и исследовательское качество модели. Фиксированное demo-число не участвует в оценке точности. Существующие результаты frontend описаны в [отчёте проверок](verification.md); ниже указаны условия будущей приёмки.

## Предварительные условия эксперимента модели

Али вместе с руководителем должен до обучения зафиксировать целевую популяцию, источник/лицензию и допустимость данных, единицу наблюдения, целевую переменную и момент её измерения, горизонт, доступные в момент прогноза признаки, пропуски, критерии исключения и возможные смещения. Для предварительного САД необходимо различить восстановление текущего значения и прогноз будущего. При отсутствии такого определения обучение и сравнение метрик преждевременны.

Порог практической полезности и допустимую ошибку согласовать до просмотра тестовых результатов. Сейчас числовой порог не установлен: придумывать медицинский допуск нельзя. Исследовательское улучшение относительно baseline ещё не означает клиническую пригодность. Методологические основания и ограничения собраны в [обзоре литературы](research/literature-review.md).

## Дизайн сравнения

1. Заморозить версию данных и список признаков, описать объём, распределения и пропуски без публикации персональных записей.
2. Разделить данные по человеку: записи одного человека не пересекают train/validation/test. Для прогноза во времени дополнительно соблюдать временной порядок. Схему split и доли выбрать после анализа доступного объёма и зафиксировать до эксперимента; при нескольких центрах рассмотреть отдельный центр как внешнюю проверку.
3. Обучать заполнение пропусков, масштабирование и отбор признаков только внутри train/fold. Подбор гиперпараметров выполнять без доступа к test.
4. Для непрерывного показателя использовать baseline B0 — среднее целевой переменной обучающей выборки; B1 — линейную регрессию на тех же признаках. Сравнить с одной обоснованной нелинейной моделью. Для MAE можно отдельно показать медианный baseline, не заменяя заранее выбранный основной baseline после просмотра test.
5. Основная метрика — MAE в единицах утверждённого показателя. Дополнительные — RMSE, R² и график предсказанного против наблюдаемого; у R² допустимы отрицательные значения. Показать n, распределение ошибок и интервал неопределённости по независимым участникам. Способ интервала выбрать и зафиксировать до анализа test; для повторных измерений ресемплировать людей, не строки.
6. По достаточности данных проверить ошибки в заранее определённых группах, пропуски и область применимости. Малые подгруппы не интерпретировать как доказательство отсутствия смещения. Размеры групп и неопределённость публиковать вместе с метриками.
7. Выполнить финальный test один раз после выбора модели. Сохранить конфигурацию, seed, версию библиотек и модели, идентификатор данных, код split, обучение и отчёт. Внешняя проверка остаётся отдельным этапом, если независимой выборки нет.

Критерий завершения исследования: независимые test-результаты модели и baseline получены одним протоколом, различие и неопределённость описаны, ограничения рассмотрены руководителем. Отсутствие улучшения — допустимый исследовательский результат; его нельзя скрывать заменой тестовой выборки.

## Инженерная проверка

| Слой и требования | Условия и действия | Критерий |
|---|---|---|
| Парсер и конфигурация, FR-02/03, NFR-02 | `npm test`; обязательность, точка/запятая, nonfinite, min/max только из метаданных, неправильные ответы | Все относящиеся unit-тесты проходят; невалидный ввод/ответ не становится прогнозом |
| Сценарий, FR-04–07, NFR-05 | `npm run test:e2e`; фикстуры 400/503/timeout, быстрая повторная отправка, отмена и поздний ответ | Один POST, ввод сохранён, устаревший результат не появляется, real не переходит в demo |
| UX и языки, FR-01/09, NFR-03/04 | Chromium desktop 1440×1200 и mobile 390×844; узкий экран 320 px; RU/KK/EN; клавиатура | Основной путь без мыши, ошибки связаны с полями, нет переполнения; серверные тексты отмечены как требующие локализации |
| PDF, FR-08 | Синтетический успешный ответ; скачивание, шрифты, отказ загрузки ресурса и повтор | Снимок ввода/результата совпадает, нового POST нет, текст RU/KK/EN читаем |
| Приватность, NFR-01 | Проверка кода и browser storage/network на синтетических данных | Нет показателей в URL, storage, аналитике и frontend-логах; demo не посылает показатели |
| Сборка, NFR-06 | `npm run typecheck`, `npm run lint`, `npm run build`; явный режим окружения | Команды проходят; отсутствие режима не включает demo неявно |
| Настоящая интеграция, FR-10 | После согласования: frontend + Spring Boot + одна закреплённая версия модели | Валидный ответ совпадает с прямым вызовом модели; ошибки, единицы, timeout/CORS и отмена проверены без подмен API |
| Производительность real | На согласованном стенде записать CPU/RAM, версии, размер payload, сеть, concurrency и число повторов | Измерены p50/p95 и доля ошибок; целевые пороги согласованы до нагрузочного прогона, сейчас не установлены |

Дополнительно нужны ручная проверка скринридером и выбранными браузерами на поддерживаемых устройствах. Наличие Playwright с эмуляцией mobile не подтверждает проверку физического телефона.

## Форма отчёта

Каждый прогон записывает дату, commit/tag, окружение, команды, входной сценарий, ожидаемый/фактический результат, лог без медицинских данных, дефекты и ссылку на исправление. Для модели дополнительно записываются данные/split/seed/baseline/метрики/неопределённость. Для реальной интеграции фиксируются версии всех трёх компонентов.

Ответственные: Санат — frontend и E2E; Оралхан — серверные и интеграционные проверки; Али — эксперимент модели; команда и руководитель — решение о достаточности свидетельств. Настоящая модель и её метрики пока не проверены.
