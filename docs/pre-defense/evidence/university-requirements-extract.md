Требования к дипломному проекту и предварительной защите

1. Основные компоненты проекта и критерии оценки

2. Требования к Git-репозиторию

В течение всего периода выполнения дипломного проекта студенты должны вести репозиторий на GitHub или GitLab. Репозиторий должен обеспечивать возможность отслеживания истории разработки проекта, индивидуального вклада каждого участника и процесса проверки результатов работы.

Шаг 1. Создание репозитория проекта

Создать репозиторий на GitHub или GitLab в начале работы над проектом.

Использовать понятное название, отражающее суть проекта.

Вести весь проект в одном и том же репозитории на протяжении всего периода разработки.

Допускается использование закрытого (приватного) репозитория при условии, что научный руководитель и комиссия имеют к нему доступ.

Шаг 2. Предоставление доступа и идентификация участников

Предоставить всем участникам команды и научному руководителю соответствующие права доступа.

Предоставить комиссии доступ к репозиторию до каждой предварительной защиты.

Каждый студент должен использовать собственную учётную запись и указывать идентифицируемые данные автора коммитов.

Запрещается использовать общие учётные записи для отправки результатов работы.

Шаг 3. Подготовка файла README

Файл README.md должен содержать:

Название проекта и его краткое описание.

Постановку проблемы, целевых пользователей и ожидаемые результаты.

Состав команды, обязанности участников и информацию о научном руководителе.

Границы проекта и текущий статус разработки.

Выбранные технологии.

Ссылки на проект в YouTrack и документацию проекта.

Инструкции по установке, запуску и тестированию — как только станет доступен запускаемый программный код.

Шаг 4. Организация структуры репозитория

Необходимо создать понятную структуру, включающую следующие разделы:

Исходный код (Source code): программный код приложения, организованный по компонентам.

Документация (Documentation): предложение по проекту, обзор литературы, сравнительный анализ, требования и архитектурные решения.

Диаграммы (Diagrams): редактируемые исходные файлы диаграмм и их версии в удобном для просмотра формате.

Тесты (Tests): автоматизированные тесты и вспомогательные материалы для тестирования.

Конфигурация (Configuration): описания зависимостей и примеры конфигурационных файлов.

Необходимо добавить подходящий файл .gitignore. Запрещается размещать в репозитории пароли, API-ключи, персональные данные и другую конфиденциальную информацию. В примерах конфигурационных файлов следует использовать условные значения-заполнители (placeholders).

Шаг 5. Постепенная фиксация выполненной работы

Фиксировать изменения в репозитории по мере выполнения значимых задач и подзадач.

Каждый коммит должен отражать логически завершённое изменение и иметь содержательное описание.

Изменения в документации и проектных решениях также необходимо фиксировать в репозитории.

Загрузка всего проекта непосредственно перед предварительной защитой не подтверждает непрерывность разработки.

При оценивании будет учитываться содержание и динамика вклада участников, а не количество коммитов.

Шаг 6. Связь изменений с задачами в YouTrack

Создать задачу в YouTrack для каждого значимого вида работ.

В каждой задаче указать ответственного студента, ожидаемый результат, критерии приёмки и срок выполнения.

Указывать идентификатор задачи в названии ветки, а также в описании коммита или Pull Request / Merge Request.

Добавлять в задачу YouTrack ссылку на соответствующий Pull Request / Merge Request или коммит.

Отмечать задачу как выполненную только после достижения установленных критериев приёмки.

Пример:

Задача: DIP-23 – Определение схемы базы данных.

Ветка: DIP-23-database-schema.

Коммит: DIP-23: Add initial database schema and ER diagram (Добавлена первоначальная схема базы данных и ER-диаграмма).

Шаг 7. Использование веток и Pull Request / Merge Request

Поддерживать ветку main как проверенную базовую версию проекта.

Разрабатывать изменения в отдельных ветках для конкретных задач или функциональных возможностей.

Представлять изменения на проверку через Pull Request на GitHub или Merge Request на GitLab.

В каждом запросе на слияние необходимо описать внесённые изменения, указать связанную задачу YouTrack и объяснить, каким образом была проверена выполненная работа.

В командных проектах перед слиянием изменений их должен проверить другой участник команды.

В индивидуальных проектах научный руководитель должен проверять выбранные существенные изменения на согласованных контрольных этапах.

Шаг 8. Создание тегов для каждой предварительной защиты

Для каждой стадии необходимо создавать Git-тег, идентифицирующий точную версию проекта, представленную на защите:

pre-defense-1 — первая предварительная защита;

pre-defense-2 — вторая предварительная защита;

final-pre-defense — заключительная предварительная защита.

Для каждой представленной версии необходимо предоставить:

ссылку на репозиторий;

Git-тег;

краткое описание выполненной работы;

известные ограничения;

список нерешённых задач.

Разработку следует продолжать в том же репозитории, не перемещая и не заменяя ранее созданные теги представленных версий.

Шаг 9. Демонстрация репозитория во время предварительной защиты

Продемонстрировать структуру репозитория и историю разработки.

Проследить путь выбранной задачи YouTrack до её реализации или соответствующего результата.

Объяснить индивидуальный вклад каждого участника и содержание выбранных изменений.

Показать замечания, оставленные в ходе проверки, и последующие исправления.

Объяснить назначение и принцип работы представленного программного кода.

Продемонстрировать запуск и тестирование доступной реализации.

3. Минимальные требования к 24 октября

К указанной дате репозиторий должен содержать:

Завершённый файл README.md с описанием проекта.

Предложение по проекту и описание его границ.

Обзор литературы, сравнение существующих систем и сравнение технологий.

Первоначальную спецификацию требований и критерии приёмки.

Обязательные архитектурные диаграммы, включая редактируемые исходные файлы.

Материалы прототипа или ссылку на прототип.

План проверки и оценки результатов.

Ссылку на проект в YouTrack с назначенными и приоритизированными задачами.

Подтверждение постепенного внесения вклада каждым участником команды.

На данном этапе готовое приложение не требуется.

Репозиторий должен демонстрировать, что анализ, проектирование, планирование и контроль со стороны научного руководителя уже осуществлялись.

## Таблица компонентов и критериев

| № | Компонент | Содержание представляемых материалов | Критерии оценки комиссии |
| --- | --- | --- | --- |
| 1 | Предложение по проекту (Project Proposal) | Название проекта, участники команды, научный руководитель, постановка проблемы, целевые пользователи, цель, задачи, ожидаемые результаты и границы проекта. | Насколько чётко определена проблема, реалистичны ли границы проекта и обладает ли проект достаточной инженерной сложностью. |
| 2 | Подтверждение актуальности | Интервью с потенциальными пользователями, обсуждения с заказчиком, наблюдения за соответствующими процессами или анализ имеющихся данных. Необходимо провести 3–5 обсуждений с представителями пользователей либо иметь содержательное соглашение с реальным заказчиком. | Какие доказательства лежат в основе требований и отделены ли подтверждённые результаты от предположений. |
| 3 | Обзор литературы | Критический обзор релевантных источников и структурированная аналитическая таблица публикаций. Не менее 12 содержательно использованных источников, включая не менее 8 научных публикаций. Для быстро развивающихся направлений основная часть источников должна относиться к последним пяти годам, при этом необходимо сохранить ключевые фундаментальные работы. | Какие подходы существуют, что уже известно и какие ограничения учитываются в проекте. |
| 4 | Сравнение существующих систем | Сравнение существующих систем по единому набору критериев. Необходимо рассмотреть 3–5 релевантных систем и использовать 6–10 критериев сравнения. Если сопоставимых систем меньше, это необходимо обосновать. | Почему необходимо предлагаемое решение и подтверждены ли доказательствами утверждения о возможностях и ограничениях существующих систем. |
| 5 | Сравнение технологий | Сравнение альтернатив при принятии ключевых технологических решений. Необходимо рассмотреть не менее трёх ключевых технических решений, для каждого из которых следует определить 2–3 обоснованные альтернативы. Например: серверная платформа, хранение данных и способ взаимодействия компонентов. | Насколько обоснован выбор технологий с учётом требований проекта. |
| 6 | Спецификация требований | Функциональные и нефункциональные требования, приоритеты и критерии приёмки. | Можно ли проверить выполнение каждого обязательного требования. |
| 7 | Архитектура и диаграммы | Согласованный комплект диаграмм и описание архитектуры: 1) диаграмма контекста системы; 2) диаграмма вариантов использования (Use Case Diagram); 3) предварительная диаграмма компонентов (Component Diagram). | Согласованы ли требования, компоненты, данные и сценарии работы системы. |
| 8 | UX / прототип | Макеты ключевых пользовательских сценариев. Для проектов без пользовательского интерфейса — примеры API, команд либо входных и выходных данных. | Понятно ли, как пользователи или внешние системы будут взаимодействовать с решением. |
| 9 | План проверки и оценки | План тестирования, метрики результатов, условия измерений и базовое решение для сравнения. | Каким образом будет продемонстрировано достижение цели проекта. |
| 10 | Управление проектом и риски | Git-репозиторий, проект в YouTrack, распределение обязанностей, этапы проекта, риски и зависимости. | Можно ли отследить ход выполнения проекта и чётко ли определены дальнейшие шаги. |
| 11 | Обратная связь научного руководителя | Отзывы научного руководителя по ключевым результатам и решениям, а также описание действий по устранению замечаний. | Проверил ли научный руководитель содержание работы и привела ли проверка к существенным улучшениям. |
